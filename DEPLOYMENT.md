# WriteSpace Deployment Guide

WriteSpace is a static Vite 5 and React 18 single-page application. All application data, including accounts, sessions, and blog posts, is stored in the user's browser using `localStorage`. No API server or database is required.

## Prerequisites

- Node.js 18 or later
- npm
- A Vercel account for hosted deployments
- Access to the Git repository

## Local Production-Build Verification

Install dependencies using the committed lockfile when available:

```bash
npm ci
```

If no lockfile is available, use:

```bash
npm install
```

Run the test suite:

```bash
npm test -- --run
```

Create a production build:

```bash
npm run build
```

The generated static assets are written to `dist/`.

Serve the production build locally:

```bash
npm run preview
```

Vite prints the preview URL, typically `http://localhost:4173`. Verify the application using that URL rather than the development server.

## Environment Variables

WriteSpace requires no runtime or build-time environment variables.

The repository includes `.env.example` to document this explicitly. Do not add secrets to client-exposed Vite variables. Any future variable accessed by application code must use the `VITE_` prefix and will be included in the browser bundle.

No environment variables need to be configured in Vercel for the current application.

## Deploying to Vercel

### Import the Repository

1. Sign in to Vercel.
2. Select **Add New** and then **Project**.
3. Import the WriteSpace Git repository.
4. Select the repository root as the project root.
5. Confirm that Vercel detects the **Vite** framework.
6. Use the following settings:
   - Build command: `npm run build`
   - Output directory: `dist`
   - Install command: `npm install`, or leave the detected default
7. Leave the environment-variable section empty.
8. Select **Deploy**.

Vercel creates a preview deployment for supported branch and pull-request workflows and a production deployment when the configured production branch is deployed.

### Production Deployment

After validating a preview deployment, merge or promote the approved commit according to the repository's release process. Confirm that the production deployment uses the expected commit before completing smoke checks.

## Single-Page Application Rewrites

Client-side routes are managed by React Router. Direct requests to routes such as `/blogs`, `/write`, `/blog/:id`, `/edit/:id`, `/admin`, and `/users` must return `index.html` so the browser router can resolve them.

The repository's `vercel.json` configures this fallback:

```json
{"rewrites":[{"source":"/(.*)","destination":"/index.html"}]}
```

Keep this file at the repository root. Without the rewrite, opening or refreshing a client-side route may return a Vercel 404.

Static assets generated by Vite continue to be served normally by Vercel.

## Post-Deployment Smoke Checks

Use a fresh browser profile or clear site data before the guest checks.

1. Open `/` and confirm that the WriteSpace landing page renders.
2. Open `/login` and `/register` directly.
3. Open `/blogs` while signed out and confirm redirection to `/login`.
4. Refresh `/login` and another client-side route to confirm the SPA rewrite does not return a 404.
5. Register a temporary local user with a non-sensitive password.
6. Confirm that registration redirects to `/blogs`.
7. Create a post and confirm that it appears on the blogs page.
8. Open the post, edit it, and confirm the changes persist after a refresh.
9. Cancel a delete operation and confirm that the post remains.
10. Delete the temporary post and confirm that it is removed.
11. Log out and confirm that protected routes redirect to `/login`.
12. Log in with the demo administrator credentials `admin / admin`.
13. Confirm access to `/admin` and `/users`.
14. Confirm that an unknown route redirects to `/`.
15. Check the browser console for unexpected errors.
16. Verify the layout and navigation at mobile and desktop viewport sizes.

Data created during smoke testing is local to the browser and deployment origin. It does not affect other users or environments.

## Operational Considerations

### Browser-Local Data

WriteSpace does not synchronize data between browsers, devices, users, preview deployments, or production domains. Each origin has separate `localStorage`.

Changing the deployment domain creates a different storage origin, so existing browser data will not automatically appear on the new domain.

Clearing browser storage, using private browsing, or removing site data deletes local WriteSpace accounts, sessions, and posts. There is no server-side backup or recovery mechanism.

The application stores demo passwords without encryption. Use only non-sensitive test credentials.

### Monitoring

Because there is no backend, database, or server-side application process, operational checks should focus on:

- Vercel deployment and build status
- Static asset availability
- SPA route fallback behavior
- Browser console errors
- Core authentication and post-management flows
- Browser storage availability and quota errors

## Rollback

Vercel retains previous deployments.

1. Open the project in the Vercel dashboard.
2. Select **Deployments**.
3. Find the most recent known-good production deployment.
4. Review its commit and smoke-check status.
5. Use Vercel's **Promote to Production** or rollback action.
6. Repeat the production smoke checks after promotion.

Alternatively, revert the faulty commit in Git and deploy the revert through the normal release workflow.

A rollback changes the deployed application assets but does not migrate, restore, or delete browser `localStorage`. Avoid changing local storage keys or stored record shapes without a compatibility or migration plan.

## CI/CD Recommendations

Run the following checks for every pull request and production-bound commit:

```bash
npm ci
npm test -- --run
npm run build
```

Recommended pipeline behavior:

- Use a supported Node.js version, preferably Node.js 20 LTS.
- Use `npm ci` when a lockfile is committed.
- Fail the pipeline on test or build failures.
- Cache npm downloads without committing `node_modules`.
- Create Vercel preview deployments for pull requests.
- Require review and successful checks before merging.
- Run smoke checks against the preview deployment.
- Restrict production deployment to the protected production branch.
- Keep Vercel production-promotion permissions limited.
- Record the deployed commit SHA for rollback traceability.
- Do not configure secrets unless a future feature requires them.
- Review any future `VITE_` variable as public client-side data.
- Add automated browser end-to-end tests for critical routes if the deployment workflow grows.

For deterministic deployments, commit the npm lockfile and keep dependency updates under review.
